# CountyIdle 系统规格

> 本文是 [01_game_design_guide.md](/E:/2_Personal/Finally/docs/01_game_design_guide.md) 的下位法。  
> `01` 裁决“这款游戏为何成立、主线往哪里收、哪些方向一律不收”；本文裁决“当前版本的系统如何落地、如何结算、如何观察、如何守边界”。  
> 若本文与 `01` 有冲突，**一律以 `01` 为准**。  
> 若本文与运行时代码冲突，应以“当前实现 + 已验证行为”为准，并回写本文修正。

## 0. 文档地位与使用裁定

- 本文只记录当前版本的核心系统法则，不承担灵感记录、草案堆放或实现备忘的职责。
- 任何系统若要进入主线，必须先回答它如何服务 `01` 中的三大体验支柱：
  - 宗门运营
  - 弟子调度
  - 挂机自动运转
- 任何系统若不能落在 `01` 中的三层空间之一，就不应写成主规格：
  - 山门内部
  - 外域周边
  - 长期成长
- 任何细到“面板结构、数值常量、世界生成权重、存档字段迁移”的内容，若不影响主法则，都不应反客为主挤占正文。

## 1. 项目基线与玩家可见语义

### 1.1 项目基线

- 项目：`CountyIdle`
- 引擎：`Godot 4.2+`
- 语言：`C# + .NET 8`
- 当前玩家身份：浮云宗掌门 / 宗主
- 当前经营主视角：天衍峰
- 当前组织骨架：天衍峰为主视角，青云峰三大总殿为总协同中枢

### 1.2 世界观与术语优先级

- 世界观锚点、组织结构、术语门禁，以 [09_xianxia_sect_setting.md](/E:/2_Personal/Finally/docs/09_xianxia_sect_setting.md) 为准。
- 玩家可见语义必须统一为：
  - `浮云宗`
  - `青云峰`
  - `天衍峰`
  - `阵堂 / 庶务殿 / 传法院 / 青云总坊接口`
  - `门人 / 弟子 / 附庸 / 职司 / 传承 / 护山 / 外务`
  - `修为 / 境界 / 功法 / 技艺 / 身份`
- `County / Town / Prefecture` 等旧词只允许作为代码层兼容命名存在，不代表玩家可见设定。

### 1.3 当前玩家可见语义映射

| 技术名 | 对外语义 | 当前裁定 |
| --- | --- | --- |
| `Population` | 门人总量 / 宗门人口池 | 不是城民人口，而是浮云宗生态中的可调配人口总量 |
| `Farmers / Workers / Merchants / Scholars` | 阵材 / 阵务 / 总坊外事 / 推演职司汇总 | 当前为内部结算汇总层，不作为玩家主交互对象 |
| `ContributionPoints` | 宗门贡献点 | 宗门内部调度与建设货币 |
| `Research` | 传承研修 / 功法推演 | 不是现代科技研发 |
| `Breeding` | 灵根苗子培育 / 后辈培育 | 属于长期成长系统 |
| 修为 / 境界 | 修为层级（炼气 / 筑基 / 金丹 / 元婴 / 化神+） | 控制任务风险上限、外务层级与可承担职司 |
| 功法 / 法门 | 主修法门 / 传承路线 | 决定成长路径与技艺解锁倾向，不是数值等级 |
| 技艺 / 术门 | 主修技艺（炼丹 / 炼器 / 阵法 / 符箓 / 剑道 / 体修 / 御兽 / 灵植 / 卜算 / 医道） | 表示擅长方向，影响任务风格与收益 |
| 身份 / 归属 | 门人身份（门人 / 执事 / 真传 / 客卿 / 外域修士） | 表示组织归属与职责位置，不代表价值高低 |
| `Combat` | 外务历练 / 护山战备 | 同时覆盖外域与宗门防务语义 |
| `CountyEvent` | 宗门见闻 / 山门事件 | 属于宗门活态反馈，不是通用随机事件 |


### 1.4 修为 / 功法 / 技艺 / 身份 的 UI 表现规则（现行准则）

- 概览展示使用三段式修为：`初阶(炼气/筑基)`、`中阶(金丹/元婴)`、`高阶(化神+)`，用于快速判断可承载风险层级。
- 概览文案顺序固定为：`身份 -> 修为 -> 功法 -> 技艺`，用于快速对齐职司判断。
- 概览行模板：`身份 · 修为 · 功法 · 技艺`，用于名册/列表快速对齐。
- 详情行模板：`身份: {身份} | 修为: {境界} | 功法: {主修法门} | 技艺: {主修技艺}`。
- 派遣判定说明：任务门槛由 `修为` 决定，路线倾向由 `功法` 决定，具体胜任度由 `技艺` 决定。
- 详细展示保留完整境界名，并允许补充次要技艺标签，避免把修为当作唯一能力。
- 门人条目至少显示：`身份`、`修为(三段或完整)`、`主修功法`、`主修技艺`，以支持职司与任务指派判断。
- 任何 UI 文案禁止使用“等级/职业高低”叙述，统一以“修为/境界/功法/技艺/身份”描述成长与分工。
- 若暂未生成功法/技艺/身份细分，允许显示“待定功法/待定技艺/待定身份”占位，但不得回退为“职业/等级”。
- 技艺标签显示遵循“主修优先、上下文优先”：战备/历练面板优先展示战斗向技艺（剑道/体修/阵法/符箓/御兽）；内务/资源面板优先展示生产向技艺（炼丹/炼器/灵植/医道/阵法）。
- 若无上下文或空间不足：仅展示主修技艺，其余通过详情或悬停展示。
- 若未生成主修技艺：显示“待定技艺”占位。
- 全局表单控件（`CheckBox / CheckButton / OptionButton / HSlider / VSlider / Tree`）的默认图标资源统一由 `CountyIdle/themes/HanCourtyardTheme.tres` 从 `CountyIdle/assets/ui/icons/` 读取；备用修仙主题 `CountyIdle/themes/xianxia.tres` 也需保持同套 SVG 接线，避免切换主题后回退到 Godot 默认控件图标。
- 局部 `VisualFx.gd` 如需覆盖表单控件图标，只允许复用共享 SVG 资源，不得回退为运行时纯色占位，以免主题口径与卷册表现割裂。
- `godot-css-theme` 在本项目中的用法裁定为“CSS 源文件导入成 Godot `Theme` 资源后，局部挂到卷册子树”，不是浏览器式运行时 DOM/CSS 树；当前落点以 `DisciplePanel -> res://ui/xianxia.css` 为基准。
- 若需要局部视觉变体，优先使用 `theme_type_variation` 挂接 `NodeType + ClassGroup` 变体（如 `PanelContainerJade`、`ButtonGhost`），避免把节点 class 逻辑散落为运行时 metadata 约定。

- 弟子名册字段与展示模板以 `docs/10_ui_icon_guide.md` 的 4.1 为准；语义归口见 `docs/16_cultivator_classification_design.md` 的 16 节。

## 2. 核心主轴与系统总法则

### 2.1 核心主轴

当前版本的一切系统都必须服务于以下主轴：

1. 经营山门，立住资源、堂口、人口与秩序基础
2. 收人、育人、分人，让宗门真正拥有可用之人
3. 指派门人去修炼、历练、采炼、行商、守山、办差
4. 门人的行动带回收益、损耗、成长、事件与风险
5. 玩家依据结果重排宗门结构、开发新地、改换治峰方向
6. 宗门因此获得更强的自转能力与更大的外伸空间

任何绕开这条主轴单独求爽的系统，只能是侧枝，不得作为本文核心规格。

### 2.2 三条系统总法

- 系统必须让宗门更像一个活的组织，而不是更像一张表。
- 系统必须让玩家能读懂“为何得此果”，而不是只看见跳动结果。
- 系统必须让手动裁决与挂机运转能自然接力，而不是彼此打断。

### 2.3 新系统准入条件

任何新系统进入本文前，至少要先满足以下四条：

- 它明确强化宗门运营、弟子调度或挂机自动运转中的至少一项
- 它明确落在山门内部、外域周边、长期成长中的至少一层
- 它能回流到现有飞轮，而不是形成孤岛玩法
- 它不破坏 `01` 中的伦理、题材与边界要求

## 3. 三层空间的系统落点

### 3.1 山门内部

山门内部是当前版本最优先、最稳定、最常驻的系统层。

当前应由以下系统承载：

- 堂口建设、升级与职能分化
- 库藏、资源链、法器与材料周转
- 门人驻留、修炼、生产、庶务、恢复
- 护山阵务、基础秩序与内务调拨
- 宗主中枢、法令、贡献点与内务治理

系统要求：

- 山门系统必须回答“天衍峰今日凭什么活、凭什么稳、凭什么能再往前一步”。
- 任何山门系统都不得退化成“纯建筑摆放小游戏”。
- 山门系统的结果必须能回写到门人状态、外域行动或长期成长中的至少一项。

### 3.2 外域周边

外域是宗门把峰内秩序伸向峰外的系统层。

当前应由以下系统承载：

- 原材来源与附庸供给
- 青云总坊接口、商路与外务回流
- 历练、采炼、行商、驻守与附庸往来
- 妖患、袭扰、威胁与扩张机会
- 宗门护持关系与外域影响范围

系统要求：

- 外域不是风景图，也不是资源井；它必须对宗门形成压力与回报的双向关系。
- 外域系统必须能把结果回流到山门库存、门人状态、威胁压力或长期成长。
- 不允许把凡俗势力、附庸据点写成可随意牺牲的“资源块”。

### 3.3 长期成长

长期成长是“宗门最终成为什么门派”的系统层。

当前应由以下系统承载：

- 传承研修与技艺积累
- 灵根苗子与后辈培养
- 真传 / 英雄单位的成长预留
- 宗门方向分化
- 护山体系与长期势力格局

系统要求：

- 长期成长不能只表现为总量变大，必须体现方向、代价、门风与层级差异。
- 长期成长必须与山门内部和外域周边形成双向耦合，而不是单独拉一条后期数值线。

## 4. 三大体验支柱的系统约束

### 4.1 宗门运营

宗门运营是整个系统群的地基。

当前版本必须保证：

- 玩家一直在经营宗门本身，而不是借壳去玩别的类型
- 建设、资源、库藏、治理、防务、外务之间存在互相喂养关系
- 贡献点与灵石承担不同职责，不得退化成一切都只花一种货币
- 宗门不是背景板，而是所有系统结果最终回流的对象

### 4.2 弟子调度

弟子调度是将纸面规划变成宗门行动的系统轴。

当前版本的裁定是：

- 玩家不以逐人逐秒微操为主
- 玩家也不能完全跳过“用什么人做什么事”的判断
- 当前运行版允许通过职司汇总层做兼容结算
- 但所有调度系统都必须朝“门人承担真实职责”这一方向收口

当前门人相关系统至少应覆盖：

- 人口池与基础分层
- 调度与任务承担
- 修炼 / 历练 / 办差 / 驻守的用途分化
- 长期培养对象的识别与回报

### 4.2.1 弟子谱交互指令（一期）

当前运行版允许玩家在弟子谱中对单个弟子下达轻量交互批注，用于把“个体重点培养”接到聚合结算。

一期裁定如下：

- 批注档位仅有 `常制观察 / 外务候补 / 执事培养`
- `常制观察` 不提供额外结算修正，只保留卷册跟踪
- `外务候补` 影响外务历练的队伍战力与外务回流
- `执事培养` 影响内务执行效率与贡献回流
- 启蒙新苗只允许随卷观察，不直接列入外务或执事重点名册
- 该系统属于“个体重点名册折算层”，不是正式逐人排班系统

二期补充裁定：

- `执事培养` 对内务类条目提供额外执行效率修正，但不越权影响纯外务条目
- 治宗册中的“执事落实”摘要、职司摘要与条目详情必须能解释当前是否存在“执事培养补位”

三期补充裁定：

- 系统会从 `执事培养` 名册中自动筛选候选弟子，为当前内务类条目匹配补位执事
- 匹配依据至少包括：当前条目侧重、弟子执行、悟性、贡献与职司匹配度
- 弟子谱与治宗册必须能读取同一套自动补位结果，避免两边口径不一致

### 4.2.2 弟子修炼卷（十四期：结果页专精回响）

当前运行版允许玩家通过独立“修炼卷”为单个弟子登记一条主修安排，并在每次时辰结算时同时折算为聚合收益、长期成长进度、近时履历、温和的个体表现回映，以及基于主导火候归纳出的专精路数摘要/批语；同时支持从弟子谱直接跳转定位，并把这些路数继续接入外务候补、执事培养与具体内务任务的轻量差事优势联动；当长期火候成形后，还会周期性写出面向玩家可见的修炼感悟札记，并在札记触发时顺带结出一缕轻量机缘。此前卷面已重构为“弟子阵眼 + 玉简法门矩阵”的全屏沉浸式空间布局，并依据主导火候与次强火候把同一路数继续细化为更明确的专修分支，再把这些分支映照到更具体的功法/技艺专精名与分支成形履历；本轮继续让专精不只是称谓，而是落成更明确的轻量效用。

十四期裁定如下：

- 修炼卷当前登记 `技能修炼 / 功法打磨 / 技艺练习 / 打坐修炼` 四类主修安排
- 同一弟子同一时刻只保留一条主修安排；再次点击当前项可撤销，恢复常制修行
- 修炼安排以 `弟子ID -> 修炼类型` 的映射方式写入 `GameState`，必须支持旧存档缺省字段兼容
- 主界面底栏可直接打开修炼卷；若从弟子谱跳转，则修炼卷必须优先定位到当前选中弟子
- 修炼卷界面必须采用“左侧弟子名册 + 当前阵眼 HUD，右侧 2x2 玉简法门矩阵”的空间化布局，不再退回单列报表式纵向表单
- 左侧上半层必须提供可滚动且卡牌化的弟子点名册，允许玩家直接点名切换对象，而不是只靠上一位/下一位按钮循环翻页；点名册应至少能快速读出字章、境界、当前主修与专修分支短签
- 左侧下半层 HUD 必须显眼呈现当前弟子阵眼、修为/差事标签、四条长期火候进度条，以及当前安排/路数/近时感悟摘要
- 右侧四张玉简卡必须支持整卡点击切换主修，并通过高亮边框、印章或等价视觉反馈清楚标示当前敕令
- 弟子谱详情与修炼卷必须读取同一份修炼安排数据，避免“卷内显示”和“修炼卷登记”口径不一致
- 小时结算顺序中，修炼卷收益必须插在 `EconomySystem` 之后、`ResearchSystem` 之前，以便修炼产生的研修可在同一时辰参与突破判定
- `技能修炼`：时辰结算折算少量 `Research` 与 `ContributionPoints`
- `功法打磨`：时辰结算折算更高的 `Research`
- `技艺练习`：时辰结算折算少量 `IndustryTools` 与 `ContributionPoints`
- `打坐修炼`：时辰结算折算少量 `Happiness`，并对 `Threat` 提供轻微缓冲
- 四类安排还必须分别累计逐弟子长期成长进度：`根基磨砺 / 功法火候 / 技艺手感 / 静修积气`
- 长期成长以 `弟子ID -> 进度值` 方式写入 `GameState`，必须支持旧存档缺省字段兼容
- 弟子谱与修炼卷必须读取同一份长期成长数据，并能显示当前火候摘要
- 修炼卷还必须记录近时履历，至少覆盖：主修切换、关键火候跃迁
- 近时履历以 `弟子ID -> 最近若干条文本记录` 的方式写入 `GameState`，旧存档缺省字段必须兼容
- 弟子谱与修炼卷必须读取同一份近时履历，至少能展示最近一条摘要与最近数条回看
- 长期火候必须对弟子个体表现形成温和联动：`功法火候 -> 悟性/战修`、`技艺手感 -> 匠艺/执行`、`静修积气 -> 心境/气血`、`根基磨砺 -> 执行/气血/战修`
- 上述联动允许影响 `DiscipleRosterSystem` 派生属性与卷册显示，但当前阶段仍不直接写回永久基础属性字段；更复杂的养成分支放到后续阶段实现
- 弟子谱与修炼卷还必须根据四类长期火候的主导项，自动归纳当前弟子的培养路数，并至少提供一个短摘要与一句路数批注
- 当前专精差异化先采用轻量表达：`功法火候 -> 悟性/战修偏盛`、`技艺手感 -> 匠艺/执行见长`、`静修积气 -> 心境/气血更稳`、`根基磨砺 -> 执行/气血更稳`
- 专精路数当前仅用于卷册批语、培养辨识与玩家读谱体验，不额外新增永久成长字段或复杂分支树
- 当主导火候形成初段后，系统还应结合“次强火候”继续分出更细的专修偏锋；例如同属 `功法火候` 仍可继续分为 `外务锋行 / 器理推演 / 讲法悟玄 / 法门专修`
- 专修分支当前不新增独立持久化字段，而是基于既有长期火候实时推导；旧存档不需要新字段迁移
- 弟子谱与修炼卷必须显式展示当前专修分支与一句分支批注，保证玩家能读出“同一路数里又更偏哪一脉”
- 当专修分支成形后，系统还应继续把当前偏锋映照到更具体的 `功法偏锋 / 主修技艺 / 辅修技艺` 专精称谓；例如同属 `外务锋行` 可映成更偏压线/巡山的功法名，同属 `炼器演法` 可映成更偏阵枢/炼器的技艺名
- 上述专精映照不新增新的弟子基础字段，而是由当前路数/分支实时推导；旧存档不需要迁移
- 弟子谱与修炼卷必须在显眼位置展示这些专精映照，避免“分支已经成形，但功法/技艺栏仍停留在泛称”
- 当专修分支首次成形或发生明显转向时，系统应补记一条专名成形履历，并允许写入主日志或弟子个人修炼履历
- 专修分支映照出的专精称谓还应继续落成更明确的轻量效用，例如 `锋行战诀` 更偏战修、`器火演诀` 更偏匠艺、`讲法玄诀` 更偏悟性、`静值守山` 更偏气血/执行
- 上述专精效用应直接并入弟子的派生个体表现，不新增新的永久基础属性字段
- 弟子谱与修炼卷必须显式展示“专精效用”摘要，避免专名只是好看却没有落地结果
- `SectTaskRules` 的任务详情、`DiscipleDirectiveSystem` 的批注结果与 `CombatSystem` 的外务战报也必须继续回显这层专精效用，避免“人物页看得到，结果页读不出”
- 专精路数不能只停留在文本展示，还必须继续参与重点差事链路：至少要影响 `外务候补` 选前列、`执事培养` 选补位与对应内务执行修正
- 当前差事优势联动先采用轻量折算：`功法火候` 更偏外务历练 / 护山巡检 / 阵法推演，`技艺手感` 更偏工坊营造 / 总坊整备 / 执事补位，`静修积气` 更偏讲法校勘 / 长线值守，`根基磨砺` 更偏田务轮值 / 巡检补位 / 稳态内务
- 专修分支应在上述基础上提供更细一层的轻量修正，例如：同为 `功法火候`，`外务锋行` 更偏外务压线，`讲法悟玄` 更偏经卷推演；同为 `技艺手感`，`炼器演法` 更偏阵枢营造，`丹火守息` 更偏细工整备
- 这类差事优势必须回显到弟子谱 / 修炼卷文案中，保证玩家能同时读到“为什么此人更适合这条职责”
- `SectTaskRules` 的任务详情与 `CombatSystem` 的探险结果日志也必须能读取当前路数相性；若已经形成专修分支，也应一并回显当前分支，避免“机制生效了但结果页读不出来”
- 当主导火候至少形成初段后，系统应按稳定节律为个别弟子生成“修炼札记 / 感悟”文本，并同时写入主界面近闻日志与弟子个人修炼履历
- 札记触发时还应按主导路数结出轻量专属机缘：`根基磨砺 -> 少量额外功绩`、`功法火候 -> 少量额外研修`、`技艺手感 -> 少量额外工器`、`静修积气 -> 少量额外民心/危兆缓冲`
- 机缘奖励必须保持“可见但不压过主链”，优先作为一缕额外收获附着在札记文本中，不新增新的存档字段或复杂事件队列
- 弟子谱与修炼卷应能在显眼位置回看“最近感悟”，避免札记只留在主日志里一闪而过
- 感悟札记与轻量机缘当前属于轻量专属事件，不新增新的存档字段；主要用于强调不同培养路线的修行手感、职责偏向与修仙氛围
- 见闻报表卷的日志分类也必须能识别这类 `修炼 / 札记 / 感悟 / 火候` 文本，避免札记写出来却在卷内难以筛读

### 4.2.3 随机弟子生成器（开发辅助）

仅用于开发与预览，不进入正式结算或存档。

裁定如下：

- 提供 `DiscipleRosterSystem.BuildRandomRoster(GameState, count, seed?)` 作为随机名册生成入口
- 生成结果只用于弟子谱样式/系统预览，不写入 `GameState`，不进入存档
- 允许传入 `seed` 以获得可复现结果；未传入则为非确定随机
- 生成字段仍遵循现有 `DiscipleProfile` 语义，不引入职业歧视叙事
- 弟子谱调试入口默认仅 Debug 构建可见，避免影响正式玩家流程

### 4.3 挂机自动运转

挂机是本项目成立条件之一，不是简化模式。

当前版本必须保证：

- 玩家下达的安排可持续执行
- 日常小波动尽量自行吸收
- 重大机会与重大风险必须留下清晰反馈
- 自动运转不能轻易把系统推入不可恢复死局
- 玩家重新接手时，能快速看懂“发生了什么、现在该治哪一步”

挂机的及格线不是“能代跑”，而是“能代宗门继续活下去”。

## 5. 时间与节奏系统

### 5.1 当前运行版硬基线

- 细时间按“现实时间持续推动游戏分钟”运行，具体换算口径由当前运行配置裁定
- 倍速范围：`x1 / x2 / x4`
- 每累计 `60` 游戏分钟触发一次小时结算
- 顶栏时间表达必须服务“宗门在动 + 岁月在压”的双重感受

### 5.2 双层时间制裁定

`01` 对时间的裁定是：

- `细时间` 负责让宗门活着
- `长时间` 负责让修仙世界有岁月

因此本文的系统约束为：

- 小时结算属于细时间层
- 日 / 月 / 季属于长时间反馈层
- 长时间只能建立在细时间累计之上，不能脱离现有运行状态另起一套世界
- 任何长时间系统若要进入当前实现，必须说明它如何从小时结算累计而来

### 5.3 会话节奏要求

当前版本的系统反馈必须支持以下会话链路：

1. 观局
2. 批令
3. 放行
4. 收报
5. 再断

因此 UI、日志、结算、事件都必须服务“让玩家判断下一手”，而不是只服务表现。

## 6. 当前核心系统群

### 6.1 治峰与内务系统

治峰与内务是当前版本最核心的主系统群。

它至少包括：

- 堂口建设与升级
- 宗主中枢与治理法旨
- 贡献点与内务流转
- 库藏与资源调拨
- 护山与秩序维持

当前裁定：

- 玩家主交互应收口到“方向、法令、法旨、取舍”层，而不是裸露的逐项人数拨杆
- 兼容层可以保留内部汇总字段，但不能回退玩家可见语义
- 内务系统必须始终与门人状态、外域行动和长期成长保持互相影响

### 6.2 门人与职司系统

当前门人系统以“宗门人口池 + 职司汇总 + 调度回流”构成最小闭环。

本文裁定：

- `Population` 对外只能解释为宗门人口池
- 当前允许存在 `Farmers / Workers / Merchants / Scholars` 作为内部兼容汇总
- 但玩家主交互应表达为职司、法旨、用途与培养方向
- 后续若实现真传、英雄实体，应视作现有门人系统的显式化，而不是另起新系统

### 6.3 产业、供养与库藏系统

产业系统不只是产能系统，它是宗门供养能力的体现。

本文裁定：

- 资源必须支撑建造、供养、防务、历练与长期成长
- 材料链应保持“原材 -> 加工 -> 消费 / 反哺”的可解释结构
- 仓储系统必须承担真实压力，不能只是上限装饰
- 产业系统的结果必须能解释给玩家听，而不是只在后台结算

当前材料层级方向：

- `T0 / T1` 作为当前版本主要前台层级
- 更高层材料与复杂制造可继续存在，但不得挤占主线可读性

#### 6.3.1 仓储三源产出模型（V1）

本文裁定：

- 仓储必须能区分三条产出来源：经营产出、外务收获、手动制造成品。
- 宗门仓库是“可支配库存”，只有进入宗门仓库的资源才可被建造/供养/消耗。
- 外务收获先进入“外务行囊”；手动制造成品先进入“工坊成品暂存”，两者需要显式入库。
- 经营产出在时辰结算时直接进入宗门仓库，并记录来源标签以便追溯。

#### 6.3.2 入库与消耗规则

- 宗门仓库是唯一的扣减源，扣减前必须做可支付检查。
- 行囊/成品暂存不参与自动消耗与容量计算，仅作为待入库缓冲层。
- 入库动作需在仓储卷提供入口，允许一键将暂存归入宗门仓库并清空暂存。
- 旧存档不存在行囊/成品字段时，默认视为 `0`，不得影响现有库存。

#### 6.3.3 可观测性与反馈

- 仓储卷状态区展示三源摘要：经营产出、外务行囊、工坊成品。
- 事件日志或提示条需标注来源，避免“产出从何而来”不透明。

### 6.4 传承与长期成长系统

传承系统属于长期成长主轴，而不是附属数值条。

本文裁定：

- 研修系统对外统一解释为传承 / 功法推演
- 传承必须与堂口、门人、外务、护山形成联动
- 灵根苗子培养属于长期成长，不得写成纯概率抽奖系统
- 真传 / 英雄系统若进入实现，必须服务宗门史与组织感，而不是单角色爽感

### 6.4.1 功法命名与研修解锁（现行口径）

研修节点命名规则：

- 研修节点命名遵循：`传承关键词 + 路线/法门名`，示例：`青云·丹诀入门`、`天衍·玄剑进阶`、`阵堂·八极阵经`。
- 节点名称只表达路线与法门，不直接写数值或战力词。

- 功法是传承路线的名称标签，不是数值等级或技艺强弱。
- 功法命名由“传承路线关键词 + 法门名”组成，优先使用宗门/峰堂/道统语义，避免现代科技或职业称谓。
- 功法名允许分层：入门功法 -> 主修法门 -> 真传心法（仅语义层，不强行数值）。
- 研修系统负责解锁“功法路线节点”；节点可授予技艺标签或开启高阶职司门槛，具体数值留在系统实现。
- 技艺由“功法路线 + 修为门槛”共同解锁，避免单一研究点直接授予战力。
- 未生成功法时统一展示“待定功法”。

### 6.5 外务、历练与护山系统

外务系统负责把山门与外域接起来。

本文裁定：

- 历练不是纯战斗玩法，而是收益、损耗、成长与风险的外域回路
- 护山不是单一防御玩法，而是宗门秩序、威胁压力与长期护持责任的体现
- 外务系统必须与资源、门人、传承、威胁形成闭环
- 不允许把外务系统做成脱离宗门经营的纯关卡制玩法

### 6.6 装备与法器系统

装备 / 法器系统只能作为门人、历练、供养链的下位支撑。

本文裁定：

- 装备系统不能喧宾夺主，抢走宗门经营与门人调度的主位
- 其价值必须回流到历练、生存、防务、生产效率或培养方向
- 若当前实现以掉落和工具制作为主，也应保持未来可向法器体系平滑过渡

### 6.7 事件系统

事件系统必须服务“宗门是活的”这一核心判断。

本文裁定：

- 事件必须来自山门、外域、传承、护山、门人状态等真实系统来源
- 事件不是独立的随机噪音
- 事件至少要提供以下三者之一：
  - 结果反馈
  - 风险警示
  - 新的判断空间

## 7. 结算顺序、状态安全与可观测性

### 7.1 当前小时结算顺序

当前运行版固定顺序为：

`Industry -> Resource -> Economy -> Research -> Population -> Breeding -> Combat -> CountyEvent`

裁定：

- 这是当前主结算链，不得随意交换
- 任何新子系统若要插入，必须证明它不会打断主链可读性与稳定性
- 小时结算完成后，UI 读取的必须是 `GameState.Clone()` 发布结果

### 7.2 GameState 安全约束

以下条目属于“破了就算 bug”的硬边界：

- 人口、岗位、建筑数量、工具库存不得出现负值
- 资源扣减路径必须有可支付检查
- 玩家可见库存必须保持可解释
- 新字段必须保证旧存档可读
- 自动运转不得轻易把系统推入不可恢复死局


### 7.2.1 GameState / Disciple 数据结构草案（文档）

仅用于对齐 UI/系统语义的结构草案，不代表最终存档格式；新增字段必须保证旧存档可读。

GameState（与弟子相关的最小结构）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `Disciples` | list<DiscipleRecord> | 弟子名册列表 |
| `DiscipleVersion` | int | 数据结构版本号（仅用于兼容与迁移判断） |
| `DiscipleDirectives` | map<int,string> | 弟子交互指令表（`弟子ID -> 常制/外务候补/执事培养`） |
| `DiscipleCultivationAssignments` | map<int,string> | 弟子修炼安排表（`弟子ID -> 技能修炼/功法打磨/技艺练习/打坐修炼`） |
| `DiscipleSkillTrainingProgress` | map<int,double> | 技能修炼对应的根基磨砺进度 |
| `DiscipleTechniquePolishProgress` | map<int,double> | 功法打磨对应的功法火候进度 |
| `DiscipleCraftPracticeProgress` | map<int,double> | 技艺练习对应的技艺手感进度 |
| `DiscipleMeditationProgress` | map<int,double> | 打坐修炼对应的静修积气进度 |
| `DiscipleCultivationHistory` | map<int,list<string>> | 弟子近时修炼履历（主修切换 / 阶段跃迁等） |

DiscipleRecord（最小结构）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `DiscipleId` | string | 唯一标识 |
| `Name` | string | 显示名 |
| `IdentityTag` | string | 身份标签（门人/执事/真传等） |
| `RealmTag` | string | 修为境界标签（炼气/筑基/金丹/元婴/化神+） |
| `TechniqueTag` | string | 主修功法法门标签 |
| `SkillTag` | string | 主修技艺标签 |

DiscipleRecord（可选扩展字段）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `AffiliationTag` | string | 归属峰堂/道统/外域标签（可空） |
| `SecondarySkillTags` | list<string> | 次要技艺标签（可空） |
| `DirectiveTag` | string | 当前交互批注（常制观察/外务候补/执事培养） |
| `CultivationAssignmentTag` | string | 当前修炼卷安排（可空，缺省表示常制修行） |
| `CultivationProgressTags` | list<string> | 四类长期成长摘要（可空，用于 UI 展示） |
| `CultivationHistoryText` | string | 近时修炼履历摘要（可空，用于卷册展示） |
| `RealmTierTag` | string | 三段式修为标签（初/中/高，便于概览） |
| `StatusTag` | string | 当前状态标签（空闲/执行/闭关/疗伤等） |
| `OverviewText` | string | 概览文案缓存：`身份 · 修为 · 功法 · 技艺` |

派生规则与展示约束：

- `OverviewText` 为派生字段，可由 `IdentityTag/RealmTag/TechniqueTag/SkillTag` 拼接生成，不要求强制落盘。
- 若 `TechniqueTag` 或 `SkillTag` 缺失，UI 必须显示 `待定功法` / `待定技艺` 占位。
- 禁用“等级/职业高低”描述，统一用“修为/功法/技艺/身份”。

### 7.3 可观测性要求

当前系统至少要能向玩家解释：

- 这一轮宗门做成了什么
- 哪条链路开始发紧
- 哪一类风险正在抬头
- 现在最值得宗主处理的是什么

因此日志、摘要、状态提示至少要覆盖：

- 资源与供养压力
- 门人与调度结果
- 外务与威胁变化
- 长期成长推进

## 8. 地图、界面与存档的定位

### 8.1 地图定位

地图是三层空间的观察与调度载体，不是独立玩法主轴。

本文裁定：

- 宗门图服务山门内部
- 外域图 / 世界图服务外域周边
- 地图系统的职责是观察、进入、调度、反馈
- 地图不得沦为纯观光图，也不得脱离宗门飞轮自成一套玩法

- 战略地图支持“配置驱动/生成驱动”双轨；调试可用 `F8` 或世界舆图页调试入口在两套定义间切换。

#### 8.1.1 天衍峰院域坊局与全格检视（一期）

本文裁定：

- 天衍峰山门图的任意 hex 都必须可点选；若未命中场所锚点，则进入“院域坊局检视”分支，不再退回纯背景格。
- 天衍峰山门图的产业建筑显影需与建筑数量联动：按“每 2 座建筑映射 1 个锚点建筑（至少 1 个、上限 4 个）”生成可见锚点；建造时优先落在当前选中地块，未选中则按推荐落点自动落建；落点写入 `GameState` 并随存档持久化，读档后自动复原。
- 每个院域地块至少维护以下固定底盘字段：`RegionName`、`ContentKind`、`QiAffinityText`、`BaseQiCapacity`、`QiRecoveryPerHour`、`BuildSlotCount`、`FeatureTexts`。
- 每个院域地块的一期坊局层至少维护以下可变字段：`PlanStyle`、`SubBuildings`、`TotalQiDemand`、`QiCongestion`、`SynergyScore`、`Stability`、`SuggestedBuildType`。
- 检视器一期必须统一回答四个问题：`这里是什么`、`它现在在干什么`、`为什么顺或为什么卡`、`我现在能做什么`。
- 左侧检视器需展示地块建筑列表：锚点场所显示已落成建筑，普通院域显示坊位规划列表。
- 当前运行版至少支持三档运行时坊局调整：`主修坊局`、`协同坊局`、`稳态坊局`；切换后要立即刷新坊位摘要、灵气需求、协同分和稳定度。
- 天衍峰山门图与同族二级局部沙盘的基础地块层，必须优先直接读取 `L1_hex_tileset.tres` 作为运行时纹理来源；不允许长期维持“编辑器已有 tileset、运行时仍直接切图片 atlas”的双轨漂移状态。
- 若基础地块 atlas 本身为方形切片，运行时必须按 hex polygon 进行投影，保证玩家看到的是无缝 hex 地块，而不是原始矩形贴图区。
- 一期允许把坊局切换停留在地图局部模拟层，不强制立刻写入 `GameState` 小时结算，也不强制立刻改动存档结构；未接入结算前，相关数值视为院域规划反馈，不视为全局经济事实。
- 院域随机性来源继续限定为：`地块 traits`、`节气波动`、`低频局部事件`、`驻守差异`、`宗门缺口`；一期只允许先接入说明与规划反馈，不允许用高频随机把玩家长期规划直接打散。

#### 8.1.2 世界格二级地图入口（一期）

本文裁定：

- 世界地图的任意 hex 都必须具备“进入下一层地图”的身份语义；不允许只有少数世界站点可进入，而其余地块只是不可交互背景。
- 世界图点击链路采用 `站点优先、地块回退`：若点击命中已生成站点，则沿用该站点的 `PrimaryType / SecondaryTag / RegionId / RarityTier / UnlockTier`；若未命中站点，则必须基于当前地块的 `Biome / Terrain / Water / Wonder / Structure / QiDensity / Corruption / MonsterThreat / Fertility` 合成一份可进入的二级地图入口数据。
- 站点回退生成的一期类型至少覆盖 `Wilderness`，并允许继续映射到 `Sect / MortalRealm / Market / CultivatorClan / ImmortalCity / Ruin`；其目标不是一次性补完独立玩法，而是保证“每格可进、每格有身份、每格有风险/收益描述”。
- 点击世界 hex 后，运行时最小闭环为：`世界图点选 -> 左侧检视刷新 -> 左侧进入按钮 -> SecondaryMapView 生成下一层局部地图 -> 可返回世界图`。
- `SecondaryMapView` 一期仍可复用统一占位页，但必须能按 `PrimaryType` 显示差异化的 `核心玩法 / 主要产出 / 主要风险` 文案；`Wilderness` 不得回落到默认未分类占位文案。
- `SecondaryMapView` 在当前运行版必须包含一张按所选 world hex 语义生成的局部地图；地图生成至少要参考该格的 `Biome / Terrain / Water / Wonder / Structure / QiDensity / Corruption / MonsterThreat / Fertility` 中的可用字段。
- 世界格进入 `SecondaryMapView` 后，局部地图的基础底盘不得只退化为统一的 `Ground` 皮肤；运行时必须至少保留一层“继承自 world hex 的地形家族”口径，当前统一收口为 `Plain / Spirit / Rugged / Snow / ShallowWater / DeepWater` 六类，用于让一级图与二级图共享基础贴图分桶。
- 二级地图 external map 模式当前继续复用 `L1_hex_tileset.tres`，但选图优先级应为：`继承的地形家族 -> 局部 terrain 语义 fallback -> atlas / 纯色 fallback`，以避免雪地、荒岭、灵地进入二级地图后又全部退成同一种普通底盘。
- 在共享地形家族之外，二级地图还必须尽量继承 world hex 的方向信息：`RoadMask` 影响局部进场道路，`RiverMask / Water` 影响局部水体/水路，`CliffMask` 或高差山地语义影响 `Ridge / Hazard` 的主要压迫方向；多方向时应先合成主方向或汇合焦点，对向成对时允许生成贯通线（路/河/脊穿越），入口方向应与合成方向一致并使用稳定的非固定侧 fallback；不允许长期把入口、水体和高差都固定写死在同一侧。
- 上述局部地图在表现形态上必须与天衍峰山门沙盘保持同族：继续使用同类 hex 沙盘视图、缩放/点选节奏与地块检视习惯，只允许改变地图内容、地块语义和局部布局，不另起一套完全不同的预览样式。
- 世界图一期的基础地块层当前继续复用 `L1_hex_tileset.tres`，但运行时主链已回到 `StrategicMapViewSystem._Draw()` 按 hex polygon 逐格投 atlas 区域；此前直接把世界格写入 `WorldTerrainTileLayer` 的方片排布会在六边形裁切后留下连续白缝，因此该节点目前仅保留为后续实验/备用基础设施，不再承担正式世界图底盘。道路 / 河流 / 站点 / 标签 / 选中高亮仍继续由 `StrategicMapViewSystem` 脚本叠加层承接，避免把交互反馈压进纯地块层后失真；旧版蜂窝背景网格也不再叠加。
- 世界图地形与 tileset 纹理的映射优先由 tileset custom data layer `world_terrain_family` 提供；若未配置，则回退到 `WorldTerrainTileLayer` 上的绑定脚本（如 `WorldTerrainTileBindings.gd`），最终再回退默认映射。`StrategicMapViewSystem` 必须确保 `_Draw()` 与 tile layer 共享同一映射口径。
- 世界图底盘的默认口径改为“平地留白、特色地貌显影”：普通平地 hex 默认直接透出 `background_map.png`，不再为每格都强制铺一层 L1 贴图；只有水域、雪地、荒岭、灵地，或带奇观 / 结构 / 灵脉 / 资源等需要强调地貌身份的格子，才优先进入显式地形贴图候选。
- 世界图显式地形贴图的整体密度需维持留白感：运行时应以 `空白 hex : 显式地形贴图 hex ≈ 1.618 : 1` 为目标，并用稳定的优先级筛选保证同一张世界图在重复打开时贴图分布不抖动；若特殊地貌数量天然超过该目标，可优先保留辨识度更高的格子。
- 天衍峰山门图与世界格二级地图也要沿用同一审美口径：普通 `Ground` 地面默认允许留白透出底图，不再要求每格都强制绘制 L1 贴图；`Road / Courtyard / Water` 等功能语义格继续视为必显，而 `Ground + VisualFamily` 的雪地 / 灵地 / 荒岭等重点地貌则按稳定优先级进入显式贴图名单。
- 山门图 / 二级地图的显式地貌筛选同样以 `空白 hex : 显式地形贴图 hex ≈ 1.618 : 1` 为目标；若道路、院落、水体等必显语义格已经超过该目标，可允许超出，不为了凑比例牺牲玩法可读性。
- 当前阶段允许把“世界格二级地图”停留在模板化入口层，不强制立即接入专属场景、独立结算或存档结构；但所有世界格都必须能给出下一层身份、开放层级与回流方向。

#### 8.1.3 文明式营建卷（城建建造）

本文裁定：

- 营建卷是主界面的独立建造视图，进入后主界面切换为“营建模式”，右栏纪事/试玩目标/营建清单折叠为“建筑列表 + 详情对比 + 队列/进度”布局，左侧仍保留地块检视摘要，中央地图保留缩略或背景承接。
- 建造入口必须绑定“当前选中地块”；若无选中地块，营建卷仅显示宗门总览与推荐地块提示，不允许直接建造落地。
- 建筑列表按类别分组，条目至少展示：成本、核心收益摘要、前置条件（坊位数/灵气/人口/职司/前置建筑）。
- 建造动作仍由 `IndustrySystem` 入口触发，已接入 `ConstructionQueueItem` 作为营建队列载体；队列仅在每小时结算推进，不允许按帧扣资源。
- 营建耗时按建筑类型裁定：产务/工务/商贸 `1` 时辰，研修/治务 `2` 时辰；每时辰仅推进队首一项，完工后增加建筑数量并生成“待落点”记录，由主界面落地到山门图。
- 建造队列已支持“撤销/停工”：未开工条目可撤销并退回全部消耗；已开工条目仅允许停工不退费；当前不提供改排。
- 该系统必须保持宗门经营语义，不得沦为纯建筑摆放玩法；建筑收益仍需与人口/职司/资源链联动。
- 可观测性要求：营建卷须明确显示“当前建造会影响哪些指标”，并在日志中可解释。

### 8.2 界面定位

界面的职责是组织判断，不是承载复杂玩法计算。

本文裁定：

- `Main.cs` 继续只负责组织、切换与展示
- 复杂玩法计算应留在系统层
- 弹窗、面板、图册都必须服务“观局 -> 批令 -> 放行 -> 收报 -> 再断”
- 主界面的卷册类弹窗当前实行排他规则：`设置卷 / 仓储卷 / 治宗册 / 弟子谱 / 修炼卷 / 峰令谱 / 留影录 / 见闻报表卷` 任一打开时，新的同族卷册入口应先收起其他卷册，再打开目标卷册，不允许长期叠层共存
- 当上述卷册类弹窗可见时，全局快捷键必须默认让行；除弹窗自身输入与 `Esc` 收卷外，不应再继续触发设置、仓储、速录、速启、速归或倍率等全局入口
- 右侧“天衍峰记事”继续承担主界面摘要职责；若要展开细读，应优先通过卷册式“见闻报表卷”承接，不把历史 `Event / Report` 兼容页签重新带回主地图入口链
- 双地图布局当前继续只向玩家暴露 `山门沙盘 / 世界舆图` 两个地图入口；历史兼容的 `Prefecture / Event / Report / Expedition` 页签仅允许作为隐藏兼容节点存在，不再参与现行主界面点击链或可见页签表达

#### 8.2.1 启动题屏（玉简起卷）

- 启动时允许先显示独立题屏遮罩，但不另起第二套运行主场景；正式经营入口仍以 `Main.tscn` 为准。
- 题屏负责承接 `开始 / 读取 / 设置 / MOD / 退出` 五项入口；其中 `开始 / 读取 / 设置 / 退出` 必须接到现有正式流程，`MOD` 在未立项前只允许展示占位提示，不得伪装成真实功能。
- 题屏显示期间必须暂停 `GameLoop` 的时间推进，避免玩家尚未入局时后台已经发生时辰结算。
- 题屏显示期间，主界面的全局快捷键必须默认让行；不得透传到底层 `Main` 触发探索、倍率、速存、速读等行为。
- 题屏背景可采用独立纸纹 shader、竖排诗文瀑布与玉简 hover 动效；这属于表现层壳，不改变系统结算、存档结构或卷册 authority。
- 题屏唤起的 `SaveSlotsPanel` 与 `SettingsPanel` 仍需沿用现有卷册/弹窗层级，保证遮罩、卷册与正式主界面之间的可见性与关闭路径一致。

### 8.3 存档定位

存档是运行稳定性的基础设施，不是当前主设计主轴。

本文裁定：

- 存档与读档必须服务当前宗门连续经营体验
- 存档格式与槽位能力属于运行支撑层
- 存档细节不得反客为主挤占系统主法则

## 9. 设计边界与禁止项

当前版本一律不以以下方向作为主规格中心：

- 单角色重操作 ARPG
- 纯建筑铺设、弱化门人调度的城建玩法
- 只追求效率表格、不追求宗门组织感的算表玩法
- 只追求视觉包装、不追求系统反馈可解释性的展示玩法

任何系统若出现以下倾向，应直接退回：

- 为复杂而复杂
- 强迫逐人逐秒微操
- 把门人、附庸、据点写成纯耗材
- 让题材只停留在换词层面
